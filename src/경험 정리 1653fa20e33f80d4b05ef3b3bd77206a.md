  # **졸업 프로젝트 팀 리더**
  ## 경험 내용
  캡스톤 졸업 프로젝트에서 팀 리더로서, 프론트엔드 2명과 백엔드 2명으로 구성된 팀을 직접 모집하였습니다. 에브리타임 플랫폼을 통해 각 지원자의 기술 스택과 프로젝트 경험을 면밀히 검토한 후, 팀원으로 선발하였습니다. 이후 창업 아이디어를 기반으로 한 졸업 프로젝트 주제를 선정하고, 효율적인 역할 분담과 팀 운영 방식을 계획했습니다.
  ### 문제 해결 및 역할 분담
  첫 회의에서 팀원들의 실제 역량을 확인한 결과, 팀원들의 기술 수준에 차이가 있음을 발견하였습니다. 이에 따라 각자의 경험과 강점을 분석하여 다음과 같은 역할을 분담하였습니다:
  - **백엔드:** 숙련된 백엔드 팀원이 초급 백엔드 팀원을 보좌하며 작업 진행.
  - **프론트엔드:** 제가 프론트엔드 작업을 전담하였습니다.
  - 기획 및 디자인 : 프로젝트 경험이 있긴 하지만 기초 html, css 경험만 있는 프론트엔드 팀원이 있어 이전까지의 경험을 물어본 결과 서비스 기획의 프로젝트 경험과 인턴 경험 등이 있어
    서비스 기획과 간단한 피그마 디자인을 주도적으로 담당하도록 부탁하였습니다.
  이를 통해 팀원들의 능력을 최대로 활용하며 프로젝트를 효율적으로 진행할 수 있도록 구조화하였습니다.
  ### 프로젝트 진행 및 도전 과제
  - **아이디어 구체화:** 팀원들과 함께 시장조사와 자료 정리를 통해 창업 아이디어를 구체화하고, 실행 가능한 계획으로 발전시켰습니다.
  - **소통 문제 해결:** 작업 도중 소통 문제가 발생하였으나, 정기적인 오프라인 미팅(도서관 작업)을 통해 문제를 해결하고 협업을 강화하였습니다.
  - **목표 준수:** 각 파트의 작업을 철저히 관리하며 프로젝트 마감 기한을 준수하였습니다.
  ### 성과 및 결과
  - 프로젝트는 기획부터 구현까지 성공적으로 마무리되었으며, 졸업 프로젝트 경진대회에서 **최종 4위**를 기록하며 **장려상**을 수상하였습니다.
  - 프로젝트를 통해 팀 운영 및 갈등 해결 능력을 강화하였으며, 제한된 자원과 역량을 최대한 활용하는 방법을 익혔습니다.
  본 경험은 리더십, 문제 해결 능력, 그리고 프로젝트 관리 능력을 체득한 값진 기회로, 앞으로의 프로젝트와 팀 협업에 큰 자산이 될 것입니다.
  에브리타임이라는 앱에서 팀원들을 제가 직접 구했는데 프로젝트 경험과 it 동아리 회장 경험이 있다는 팀원이 있어 섭외했으나 실제로는 html,css밖에 해보지 않아 react 이런 동적 방법을 해보지 못했고 속도도 너무 느리고, 스트레스를 많이 받아하셔서 직접 이야기해보는 시간을 가졌고, 이야기를 하며 서비스 기획 쪽에서 인턴 경험이 있고 실제로 그쪽에 흥미가 있어 취업 생각이 있다고 하여 졸업프로젝트는 창업 프로젝ㅇ트이기때문에 프로젝트의 기획 및 디자인에 대해 맡기고 검증 및 기능 정리를 함께 해줄것을 부탁하고 내가 책임지고 혼자서 프론트엔드 파트를 책임지며 끝까지 완성하였다.
  # 출시를 목적으로 한 팀 프로젝트에서의 팀원간의 갈등
  팀원 간의 갈등으로 기획자와 프로젝트의 기능 관련 의견차이가 있었다. 기획자로서의 프로젝트에 대한 에고가 있었고, 데이터 분석 정보 공유 커뮤니티라는 현재의 서비스에 ai를 통한 정보 제공이라는 기능을 하고 싶어 하셨다. 하지만 나의 입장에서는 아직 현실적인 이유로 ai에 대한 학습이 되어 있지 않았고, 아직 사이드프로젝트 수준에서 ai 기술의 도입이 경제적인 요금 문제가 있고 우선순위가 아닐 것이라고 생각했다. 그래서 이야기를 드렸으나 계속해서 ai 기능에 대한 욕심이 있어 계속해서 이 기능을 말씀하셨고 서로의 의견차이가 굽혀지지 않자 그냥 귀찮아서 그러시는 거냐고 등 조금 선을 넘는 말들을 하셨습니다. 그래서, 이런 모욕적인 말을 들었지만 서로 흥분했기에 이러다 조금 크게 싸움이 번지고 감정이 상하게 될것같아 조금 생각할 시간을 가진 뒤에 먼저 나서서 프로젝트 자체의 방향성과 기능, 그리고 팀원들과의 관계 등에 대하여 서로 깊이 이야기를 해보자고 제안을 하였습니다. 그렇게 프로젝트의 기능의 우선순위를 서로 이야기해보고 각자의 현실적인 능력과 현재의 상황등을 서로 이야기하였고, 각자의 상황과 생각이 다르기에 서로 각자의 입장을 대화 끝에 왜 이렇게 이야기했는지 서로 이해하게 되었고 먼저 우선순위인 기능들을 먼저 하고, ai 기능은 추후 춣시 후 유저들의 수요가 있을 경우 도입하는 것으로 이야기가 끝났고 그 이후 일정 정리와 계쏙 작업을 계속 성고적으로 마무리하여 출시까지 이어갈 수 있게되었습니다. 이 과정에서 각자가 생각하는 입장이 다를 수 있기에 각자의 입장만 생각하지 않고 서로 대화를 통해 이야기하고 이해하는 과정이 중요하다는 것을 깨닫게 되었씁니다.

    Dataracy(데이터러시)는 “사례를 보고 → 따라하고 → 이어가는” 단계별 흐름을 통해 데이터 분석 초심자도 쉽게 첫 발을 내딛고, 꾸준히 성장할 수 있도록 설계된 피드백 중심의 데이터 분석 커뮤니티 플랫폼입니다. 기존 데이터 분석 학습 환경에서는 ‘무엇을 분석해야 할지 막막한’ 출발선의 한계와 ‘피드백 부족으로 동기와 성장이 정체되는’ 지속성의 문제를 느낄 수밖에 없었습니다. 저는 이런 두 가지 본질적 문제를 바탕으로, 사례 기반 학습과 이어가기(Remix) 기능, 댓글 중심의 가벼운 피드백, 데이터셋 큐레이션 및 자동 태깅 시스템을 결합해, 진입장벽은 낮고, 피드백 루프는 빠르며, 재사용성이 높은 학습 생태계를 만들어냈습니다.

    이 프로젝트에서 저는 전체 아키텍처 설계와 백엔드 핵심 구현을 책임졌습니다. 도메인 지식에 기반한 DDD(Domain-Driven Design)와 헥사고날 아키텍처(Ports & Adapters)를 적용해 핵심 로직이 인프라와 분리되도록 구조화했고, CQRS 패턴으로 명령과 조회를 분리하여 시스템의 성능과 확장성을 확보했습니다. 827개의 Java 파일과 340개의 테스트 파일로 구성된 대규모 코드베이스를 구축했으며, 계층간 의존성 관리를 엄격하게 하면서도 테스트가 용이한 구조로 완성했습니다.

    데이터 처리 측면에서는 MySQL, JPA, QueryDSL을 기반으로 안정적인 영속 계층을 마련했습니다. 추가로 Kafka와 Elasticsearch를 활용해 비동기 이벤트 기반 파이프라인을 구현했습니다. 예를 들어, 프로젝트·댓글·좋아요 등 주요 변경 이벤트는 일단 DB에 반영된 후 Kafka로 발행되고, 이를 소비해 실시간으로 Elasticsearch에 색인됩니다. 이렇게 DB를 시스템의 단일 진실 공급원(SSOT)으로 삼고, Elasticsearch는 파생된 Projection 용도로 활용하는 구조를 세웠습니다. 만약 이벤트 처리에 실패하더라도 DLQ로 격리 후 재처리가 가능해, 데이터 정합성과 안정성을 동시에 확보했습니다.

    캐싱과 동시성 제어도 핵심적으로 다뤘습니다. Redis를 활용해 인기 프로젝트와 데이터셋 목록을 캐싱함으로써 조회 성능을 90% 이상 끌어올렸고, Redisson 기반 분산락 도입으로 좋아요, 댓글, 조회수 집계의 데이터 정합성도 지켜냈습니다. 특히 조회수는 Redis에 임시 집계 후 배치로 동기화하는 방식을 통해 DB 부하를 크게 줄이면서도 정보의 정확성을 유지했습니다.

    검색 및 추천 시스템은 프로젝트의 또 다른 성과입니다. Elasticsearch 기반으로 실시간 자동완성과 내용 기반 유사 프로젝트 추천, 가중치(score) 기반 랭킹을 제공하며, QueryDSL을 활용해 N+1 문제를 해결할 수 있도록 2단계 조회와 배치 집계 전략을 적용해 복잡한 검색에서도 성능을 50% 이상 개선했습니다.

    운영과 배포 부분에서는 Blue-Green 배포 체계를 도입해 dev/prod 환경 전체에서 무중단 배포와 빠른 롤백이 가능하도록 했습니다. Nginx 업스트림 전환, 헬스체크 기반 배포 검증, 상태 파일 활용 롤백 전략 등으로 안정성을 높였고, Micrometer, Prometheus, Grafana를 연결해 API 지연이나 Kafka Lag, Redis 캐시 적중률 등 다양한 지표를 실시간 모니터링했습니다. 특히 배포 직후에는 엄격한 임계치 기준을 운영하여 안정성에 한층 더 집중했습니다.

    테스트와 품질 관리에서도 체계적인 방식을 적용했습니다. JUnit5, Mockito, MockMvc를 사용해 단위, 웹, 통합 테스트를 촘촘히 구축했고, k6 도구로 로그인, 조회, 업로드 등 주요 API의 성능을 다양한 부하 시나리오로 검증했습니다. 이로써 총 1,621개의 테스트, 81.7% 코드 커버리지를 달성할 수 있었으며, 실제 성능 테스트 과정에서 레이트 리미팅과 캐시 최적화 같이 현업에서 직면하는 문제도 직접 찾아내 해결했고, 관련 경험을 꼼꼼하게 기록했습니다.

    결론적으로, 저는 Dataracy 프로젝트에서 도메인 모델링부터 아키텍처 설계, 데이터 파이프라인 구축, 분산 인프라 운영, 테스트 및 모니터링 체계까지 모든 중요한 과정에 주도적으로 기여했습니다. 이를 바탕으로 ‘초심자도 쉽게 시작하고, 피드백을 통해 성장하는 데이터 분석 플랫폼’이라는 목표를 실현하고, 기술적으로 견고하고 확장 가능한 서비스를 만들어냈습니다.

    ### ⚙️ 프로젝트 소개 및 역할
    HitZone(히트존)은 야구장을 직접 찾아가는 팬들이 각자의 선호에 맞는 최적의 좌석을 쉽게 찾고, 구장마다 다른 분위기와 정보를 한눈에 확인할 수 있도록 도와주는 서비스입니다. 최근 프로야구 관람객이 천만 명을 돌파할 정도로 관심이 높아졌지만, 실제 현장에서는 구역별 특성, 홈과 원정팀 위치 변화, 복잡한 층 구조 등 때문에 관람객이 헷갈려하는 경우가 많습니다. HitZone은 이런 불편을 해소하기 위해 “필요한 정보를 한 곳에서 모두 볼 수 있는 플랫폼”이라는 아이디어에서 시작되었습니다. 덕분에 야구 마니아는 물론 처음 직관에 도전하는 사람도 부담 없이 현장을 즐길 수 있도록 지원하고자 했습니다.

  - **'Why?'를 놓치지 않고 문제의 본질을 찾은 경험**
    **ES Projection 시스템 도입 과정**에서 문제의 본질을 파악한 경험이 있습니다.
    **초기 문제 상황:**
    - 좋아요, 댓글 카운트 업데이트 시 DB와 ES를 동시에 갱신하는 **동기 이중 쓰기** 방식 사용
    - 부분 실패(DB 성공, ES 실패) 시 불일치 발생
    - 분산 트랜잭션 부재로 롤백 불가
    - 네트워크 지연으로 API 응답 저하
    **Why? 분석 과정:**
    1. **왜 동기 이중 쓰기를 사용했는가?** → 즉시 일관성을 보장하려는 의도
    2. **왜 부분 실패가 발생하는가?** → 네트워크, ES 서버 장애 등 외부 요인
    3. **왜 롤백이 불가능한가?** → 분산 트랜잭션 미구현
    4. **왜 성능이 저하되는가?** → ES 반영을 기다리는 동기 처리
    **본질적 문제 발견:**
    - **근본 원인**: DB와 ES를 동등한 진실 공급원으로 취급한 설계 오류
    - **해결 방향**: DB를 단일 진실 공급원(SSOT)으로, ES를 파생 뷰(Projection)로 관리
    **해결책 구현:**
    - **Projection Task Queue**: DB 트랜잭션과 함께 큐에 작업 등록
    - **비동기 Worker**: @Scheduled로 주기적 폴링, 지수 백오프 재시도
    - **DLQ 시스템**: 재시도 초과 시 실패 작업 격리
    - **최종적 일관성**: DB → 큐 → ES 순서로 안전한 동기화
